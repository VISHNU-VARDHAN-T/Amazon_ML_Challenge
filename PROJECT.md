# Amazon Business Entity Resolution Challenge

## 1. Project Objective

Build an end-to-end machine learning pipeline for resolving business entities across three independent data sources.

Source 1 is the deduplicated reference source. For every Source 1 test entity, the system must identify matching records from Source 2 and Source 3.

Pipeline:

1. Data preprocessing
2. Candidate generation and blocking
3. Pairwise feature extraction
4. Matching model
5. Validation and evaluation
6. Final output generation

Required outputs:

- `matching_results.tsv`
- `candidate_pairs.tsv`

Candidate generation is important because the challenge reviews the candidate set in addition to the final matching score. The evaluation metric is macro-averaged F0.5, which gives more importance to precision than recall.

# 4. Person 2: Candidate Generation and Blocking

## Responsibility

Develop the candidate-generation system.

The goal is:

```text
High candidate recall
+
Low candidate count
```

Do not generate every possible Source 1 to Source 2/Source 3 pair.

## Blocking Strategies

### Blocking A: Exact normalized business name

Generate candidates when:

```text
normalized_name(S1) == normalized_name(S2/S3)
```

### Blocking B: Name token blocking

Use meaningful normalized name tokens to find possible candidates.

### Blocking C: Address token blocking

Use meaningful address tokens to generate additional candidates.

### Blocking D: Character TF-IDF

Represent business names and addresses using character n-grams.

Suggested initial configuration:

```text
analyzer = char_wb
ngram_range = (2, 5)
```

Retrieve only the top-k nearest candidates.

### Blocking E: Country-aware candidate generation

Country can be used as a signal.

Do not hard-code the country list to only the training countries because the test data can contain a country not present in training.

## Blocking experiments

Compare:

```text
Exact name
Exact address
Name token blocking
Address token blocking
Character TF-IDF
Hybrid blocking
```

Measure:

- Candidate recall
- Average candidates per Source 1 entity
- Maximum candidates per Source 1 entity
- Reduction ratio
- Number of true matches lost during blocking

# 5. Person 3: Matching Model and Feature Engineering

## Responsibility

Build the pairwise feature extraction system and final matching model.

The input to this component should be the candidate pairs generated by Person 2.

## Pairwise Features

### Name features

Investigate:

- Levenshtein similarity
- Jaro-Winkler similarity
- Character similarity
- Token similarity
- Token Jaccard similarity
- Containment
- Exact normalized-name equality

### Address features

Investigate:

- Levenshtein similarity
- Character similarity
- Token Jaccard similarity
- Token overlap
- Containment
- Exact normalized-address equality

### Additional features

Use features such as:

```text
country_equal
name_length_difference
address_length_difference
name_presence
address_presence
```

## Model experiments

Start with:

```text
Logistic Regression
```

Then evaluate other permitted models if useful.

Possible candidates include:

```text
Random Forest
Gradient Boosting
Other permitted tree-based models
```

Any final model must satisfy the challenge's stated model licensing and parameter constraints.

## Training data

Positive pairs come from:

```text
train_ground_truth.tsv
```

Negative pairs can be generated from candidate pairs that are not present in the ground truth.

## Output

The model should produce a match probability for each candidate pair.

The probability is then compared against a configurable threshold.

# 13. Important Challenge Constraints

## Input format

All challenge files are TSV files.

Use:

```python
pd.read_csv(path, sep="\t")
```

## Test coverage

Every Source 1 test entity must appear exactly once in:

```text
matching_results.tsv
candidate_pairs.tsv
```

## Matching IDs

Final matches may only contain:

```text
S2-...
S3-...
```

They must not contain Source 1 IDs.

## Candidate requirement

Every ID appearing in:

```text
matching_results.tsv
```

must also appear in:

```text
candidate_pairs.tsv
```

## Singleton entities

If no valid match is found:

```text
matched_entity_ids
```

must be empty.

Do not force a match simply because a candidate exists.

## Country

Treat country as an open-set string field.

Do not hard-code the pipeline to only the countries appearing in the training data.

## External data

Do not use:

- External business databases
- Business lookup services
- Commercial entity-resolution APIs
- Government business-registration databases
- Geocoding APIs
- Internet-based business identity lookup
- External identity data augmentation

The solution must use the supplied challenge data.
